# 旧版地点缓存覆盖导航坐标：复现与修复

核验时间：2026-09-30 22:05（Asia/Shanghai）。仅在内存模拟设备存储，没有读取手机数据、环境密钥或云端数据；未上传或发布。

## 确定性原因

1. `services/api.js` 在本机模式调用 demo；浏览器的 `__preview` 也强制走 demo。
2. demo 的存储键一直为 `youban.demo.v1`。加载旧存储只补缺失表，不刷新已导入的 `place_records`。
3. 旧版 `publishPlaceCatalogue` 将目录完整复制到 `place_records`，再次导入只添加不存在的记录。更新安装包不会更新这些快照。
4. `place-engine` 原先在详情和列表均优先返回整条存储行，因此旧行没有 `point` 时也遮住新版目录中已核实的坐标。
5. 详情页先渲染静态目录，随后把 `getPlace` 结果作为整条 `_remoteRecord`。已确认坐标因此可能在加载完成后消失。
6. 原生 demo 没有地址解析云环境，缺坐标显示“位置待核实”；浏览器能用地址搜索地图，所以浏览器表现可掩盖这一问题。

未发现公共序列化对所有 `point` 做统一剥除。旧缓存已有的 12 条坐标始终保留，不能据此声称“全部地点均因缓存故障失效”。

## 实际旧版本复现

脚本加载 Git 初始提交 `d99aaba` 的真实 demo、api、seed 和目录模块，在纯内存平台依次执行 `bootstrap` 和完整分页的 `publishPlaceCatalogue`。这样生成 29 条原版导入记录，而非把当前目录随意删除坐标来模拟。

之后让当前 api 和详情页代码读取同一份内存存储。复现日志：`2026-09-30-navigation-legacy-cache-result.json`；脚本：`2026-09-30-navigation-legacy-cache-repro.js`。

- 旧版导入记录：29 条，其中 12 条有坐标。
- 本次留档时的新版目录：30 条，其中 18 条有坐标。
- 修复后从旧缓存读取：18 条有坐标，与当时新版目录一致。
- 读取操作新增存储写入：0；整个设备存储前后相等。
- 对新增坐标的各个地点，旧结果复现“地图导航”→“位置待核实”；补全后“地图导航”保持不变。

主任务仍在补充地点坐标，上述数量仅代表日志保存时的目录。

## 最小修复

在小程序与云函数共用的 `place-engine` 中增加只读解析层，对详情和列表一致生效，只添加缺失的 `point`。满足全部条件才补全：

- 同 ID 仍存在于当前目录，存储行明确启用，当前目录未下架。
- 存储行完全没有 `point` 字段；显式 `null` 和现有坐标均不替换。
- 没有运营更新、创建或投稿标记，包含已清空的署名和保留的更新时间。
- 名称、类型、城市、行政区、片区、地址、场馆、主办方、日期和活动状态仍与当前目录相同。
- 当前坐标为有限且范围有效的 GCJ-02 场所点，并带有 HTTPS 来源。

修改不清理缓存、不改存储快照、不覆盖资料文本，不改用户账号、草稿、到访、报名、收藏或运营显式清空坐标。运营地点、改址、换场馆、改期和下架信息继续按存储记录处理。没有修改详情页来强行叠加旧坐标。
